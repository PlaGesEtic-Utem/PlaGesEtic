## 1. Contexto

Al implementar el backend base (Actividades 42 y 45) aparecieron diferencias entre lo que dicen los documentos de diseño y lo que hace el código. Este registro deja cada decisión en un solo lugar, para que el diseño, el código y el Informe de Avance N.º 2 digan lo mismo.

| D9 | Cómo se suben los archivos (Alfa) | El PDF del documento de consentimiento y la evidencia firmada se envían como **`multipart/form-data`** (un archivo por pedido, máximo **10 MB**), con la librería `multer` en memoria. El servidor revisa el tipo real por los primeros bytes (documento: PDF; evidencia: PDF, JPEG o PNG) y responde 415 si no corresponde y 413 si pesa más. El archivo se guarda en el volumen Docker `almacenamiento` (`ALMACENAMIENTO_DIR`) con un **nombre aleatorio**; en la base va la **ruta relativa** y su **SHA-256** (64 caracteres). La API **nunca devuelve la ruta**, solo el hash. Se descartó la propuesta inicial de enviar el archivo en base64 dentro de un JSON: pesa un 33 % más, obliga a subir el límite del cuerpo JSON y `multipart` es lo estándar en Express. | Aceptada (19/10, Líder) | Catálogo API §8: los campos `archivo` y `evidencia` son multipart. `docker-compose.yml` (volumen `almacenamiento`) y `package.json` (`multer`). Ya implementado (commits 118130e y 2623434). El producto de almacenamiento definitivo (por ejemplo, almacenamiento de objetos cifrado) sigue pendiente en la Especificación técnica. |
| D10 | Estado vigente de un consentimiento | El estado **no se guarda: se calcula** con el último evento de cada consentimiento (de la participación y su tipo): `aceptar` o `reconsentir` → **otorgado**; `negar` → **negado**; `retirar` → **revocado**; sin eventos → **sin_registro**. Si está otorgado pero el documento aceptado ya no es el vigente (se subió una versión más nueva) → **pendiente_reconsentir**. Además, `GET /participaciones/{id}/consentimientos` entrega el **estado_general** de la participación: **retirado** (la participación está retirada), **incompleto** (falta o está negado alguno de los exigidos: el consentimiento siempre y, si era menor al inscribirse, también el asentimiento), **pendiente_reconsentir** (alguno lo está) o **completo** (todos otorgados en la versión vigente). Se mantiene `completo` (verdadero o falso) para no romper a quien ya lo usa. | Aceptada (19/10, Líder) | Catálogo API §8 (GET) y guía `docs/api/consentimientos.md`: se usa «revocado» para el consentimiento y «retirado» para la participación, como en el catálogo. La Actividad 73 bloqueará sesiones y cargas de archivos si el estado_general no es «completo». |
| D11 | Eventos válidos | **Primera decisión** de cada tipo: `POST /participaciones/{id}/consentimientos` con `aceptar` o `negar`; si ese tipo ya existe para la participación → 409 (restricción UNIQUE). **Cambios posteriores**: `POST /consentimientos/{id}/eventos`: `reconsentir` solo si está otorgado o pendiente_reconsentir y con el documento vigente (si ya está otorgado en la vigente → 409); `retirar` solo si está otorgado o pendiente_reconsentir, y en la misma transacción deja la participación en `retirado`; `negar` solo si está pendiente_reconsentir (la persona no acepta la nueva versión). **Negado** (desde el inicio) y **revocado** no admiten más eventos, y una participación retirada no admite eventos de ningún tipo → 409. El documento se indica con **`id_documento`** (como dice el catálogo): debe ser del mismo estudio y del mismo tipo → si no, 409; debe estar vigente → si no, 409; si no existe → 404. En `retirar` se puede omitir: se usa el de la última aceptación. **Todo evento** (aceptar, negar, retirar y reconsentir) lleva **evidencia firmada** → si falta, 400. Un menor necesita dos firmas: el consentimiento lo entrega su representante legal vigente (`id_representacion`) y el asentimiento, el propio menor; a un mayor de edad no se le registra asentimiento → 409. Los eventos **no se editan ni se borran** (la base lo impide para el usuario de la aplicación): un error se corrige con un evento nuevo. | Aceptada (19/10, Líder) | Catálogo API §8 (POST de consentimientos y de eventos). Ajustes en `consentimientosService.js` antes del Pull Request (ver observaciones del 19/10). Casos de prueba CP-14 a CP-25 en `backend/pruebas/consentimientos.http`. |
| D12 | Cómo se identifica a una persona | Hay **solo dos vías** para ver datos personales de un participante. Las dos quedan en la auditoría como `desenmascarar`, con su justificación y el estudio, y responden con `Cache-Control: no-store`. **1) Contacto** (`POST /participaciones/{id}/contacto`, D8): Investigador **responsable** del estudio (`estudio.id_responsable`) o Director. Recibe `motivo` (coordinar_sesion, reconsentimiento, incidente, retiro u otro; `detalle` obligatorio si es «otro») y devuelve **solo** `codigo_seudonimo`, `nombre`, `correo` y `telefono`. Si la participación está retirada, solo acepta el motivo `retiro` (409). Usa el permiso de rol nuevo `contacto_participante/leer` (Investigador con alcance de estudio; Director, global), y el servicio revisa que sea el responsable → si no, 403. **2) Desenmascarar** (`POST /identidades/{ux_lab_id}/desenmascarar`, Matriz v3, regla A1): Director, o quien tenga una autorización `ver_identidad` aprobada y vigente para ese estudio (D13). Recibe `justificacion` (al menos 20 caracteres) e `id_estudio`; la persona debe participar en ese estudio (si no, 404 sin decir si existe). Devuelve `ux_lab_id`, `rut`, `nombre`, `correo`, `telefono` y `fecha_nacimiento`. Solo el módulo de identidades descifra, y solo en estas dos rutas. Los datos descifrados nunca se guardan en la auditoría ni en los logs, y la justificación no debe incluir datos personales. | Aceptada (20/10, Líder) | Dos rutas nuevas (Actividad 56). `05_permisos_base.sql`. Catálogo API (identidades y participaciones) y guía `docs/api/seudonimizacion.md`. Casos CP-26 a CP-35 en `backend/pruebas/seudonimizacion.http`. |

Estudiante, Invitado y Soporte no pueden ver identidades (minimización de datos). Hasta ahora la autorización no le servía a nadie salvo al Director, porque el control de acceso revisa primero el permiso del rol. | Aceptada (20/10, Líder) | `05_permisos_base.sql` y, para las bases ya creadas, `backend/db/actualizaciones/act56_permisos_identidad.sql`. Mientras no existan las rutas de autorizaciones (Actividad 74), la autorización de prueba viene en `db/dev/datos_prueba.sql`. |
| D14 | Códigos de la plataforma | Cuatro códigos **independientes**: UX Lab ID `UXL-XXXXXXXX` (la persona, uso interno; regla A2), seudónimo `P-XXXXXX` (uno por persona y estudio; A9), código del paquete `X-XXXXXX` (cada exportación) y código en la exportación `E-XXXXXX` (uno por persona dentro de cada paquete; A12: la relación con la participación nunca sale de la plataforma). ## 3. Consecuencias

- D8 respeta el documento del cliente: el Director accede a la identidad solo con justificación registrada, y Asistentes, Estudiantes e Invitados no acceden a datos de contacto sin autorización formal. Al Investigador se le permite solo lo necesario para contactar a la persona, con motivo y registro, aplicando la minimización de datos.
- El Informe de Avance N.º 2 cita este ADR para explicar por qué el código y los documentos v3 difieren en estos puntos.
- Cuando D2 a D5 se aprueben, su estado cambia a «Aceptada» con la fecha de la reunión.
- D9 a D11 buscan que cada decisión de una persona quede con su documento exacto, su evidencia firmada y su huella, sin sobrescribir nada, como pide la Ley 20.120 (consentimiento informado por escrito y asentimiento de menores). La revisión formal de cumplimiento la hace Felipe Cruz el 21/10 (Actividad 55).
- Con D11, si una persona que **negó** al inicio cambia de opinión, hoy no hay cómo registrarlo en la misma participación. Se revisará con el cliente (una opción es permitir `reconsentir` desde «negado»).
- D12 y D13 cumplen la regla A1 de la Matriz v3 (la identidad no se lee por la API salvo con desenmascarar y justificación auditada) y la amplían con la excepción de contacto de D8, que entrega solo lo necesario para contactar a la persona.
- Las bases creadas antes del 20/10 deben ejecutar una vez `backend/db/actualizaciones/act56_permisos_identidad.sql` (agrega los permisos de D12 y D13; se puede ejecutar más de una vez).
- La supresión de datos personales (`POST /identidades/{ux_lab_id}/supresion`, Matriz v3 §5) no es parte de la Actividad 56: queda para la Actividad 73.
- El consentimiento de un menor necesita la representación legal ya registrada, pero la ruta `POST /representaciones` aún no existe. Mientras tanto, el caso CP-24 se prueba con el asentimiento otorgado y sin el consentimiento del representante (el resultado esperado sigue siendo «incompleto»).
- Las bases ya creadas antes del 10/10 (por ejemplo, la de pgAdmin) deben aplicar D1 con:
  `ALTER TABLE identity_schema.identidad ALTER COLUMN correo_cifrado SET NOT NULL, ALTER COLUMN correo_hash SET NOT NULL, ALTER COLUMN telefono_cifrado SET NOT NULL;`
